# Ingress를 다시 이해하기

<img width="2340" height="1334" alt="image" src="https://github.com/user-attachments/assets/7ed3b9e9-88bf-487a-89f9-aa46d8ef488d" />


프로젝트를 진행하면서 가장 이해하기 어려웠던 부분 중 하나가 Ingress였다.

처음에는 단순하게

```
Client
  ↓
HAProxy
  ↓
Ingress
  ↓
Service
  ↓
Pod
```

정도로 이해하고 있었다.

하지만 실제 환경을 구축하고 트래픽을 추적해보면서 Ingress 자체만 이해해서는 전체 흐름을 설명하기 어렵다는 것을 알게 되었다.

실제로는 다음과 같은 여러 계층이 연결되어 있다.

```
Client
   │
   │ TCP
   ▼
HAProxy
   │
   │ TCP
   ▼
NodeIP:NodePort
   │
   │ kube-proxy 규칙
   ▼
Ingress Controller Pod
   │
   │ HTTP/HTTPS
   ▼
Ingress Rule
   │
   ▼
Service
   │
   ▼
Pod
```

그리고 서로 다른 노드에 Pod가 존재한다면 마지막 단계에서 다시 Calico 네트워크가 개입한다.

```
Node1
 └─ Ingress Controller
          │
          │ Service → Endpoint
          ▼
       Pod B
          │
          │ 다른 Node
          ▼
       Calico
          │
          ▼
        Node2
          │
          ▼
        Pod B
```

따라서 이번에는 하나의 요청이 실제로 어떻게 이동하는지 순서대로 정리해보았다.

---

# 1. 전체 아키텍처

현재 실습 환경에서는 외부 사용자의 첫 번째 진입점이 HAProxy이다.

```
                         Client
                           │
                           │ 192.168.2.80:80
                           ▼
                     ┌───────────┐
                     │  HAProxy  │
                     │ 192.168.2.80
                     └─────┬─────┘
                           │
                    Health Check
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
        Node1:30080   Node2:30080   Node3:30080
             │             │             │
             └─────────────┼─────────────┘
                           │
                    NodePort Service
                           │
                           ▼
                 Ingress Controller Pod
                           │
                      HTTP Request
                           │
                           ▼
                     Ingress Rule
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          main-svc     notices-svc    about-svc
             │             │             │
             ▼             ▼             ▼
            Pod           Pod           Pod
```

!/assets/image_1fef6e64-4734-4011-8f16-e6b3da977991.png

여기서 중요한 점은 HAProxy와 Kubernetes Ingress는 로드밸런싱을 하는 대상이 다르다는 점이다.

HAProxy는 현재 환경에서 외부 요청을 Kubernetes NodePort까지 전달하는 L4 진입점 역할을 하고, Ingress Controller는 그 이후 HTTP 요청을 분석하여 Host와 Path 등의 규칙에 따라 Kubernetes Service로 전달한다.

Kubernetes 공식 문서에서도 Ingress는 HTTP/HTTPS 트래픽을 Service로 연결하기 위한 규칙이며, 실제 동작은 Ingress Controller가 구현한다고 설명한다.

출처: https://kubernetes.io/docs/concepts/services-networking/ingress/

---

# 2. HAProxy에서는 아직 HTTP Path를 판단하지 않는다

사용자가 다음 URL로 요청한다고 가정한다.

```
http://192.168.2.80/notices
```

처음 HAProxy가 받는 것은 TCP 연결이다.

```
Client
192.168.2.100:59992
       │
       │ TCP SYN
       ▼
HAProxy
192.168.2.80:80
```

HAProxy는 현재 설정에 따라 정상 상태인 Kubernetes Node를 선택한다.

예를 들어 Node2가 선택되면:

```
Client
192.168.2.100:59992
       │
       ▼
HAProxy
       │
       │ TCP
       ▼
192.168.2.62:30080
```

이 단계에서는 아직 /notices를 기준으로 Kubernetes Service를 선택하는 것이 아니다.

즉,

```
HAProxy
  ↓
Node2:30080
```

까지는 주로 L4 수준의 연결 전달이라고 볼 수 있다.

---

# 3. NodePort는 모든 노드에 존재하는 논리적인 진입점이다

여기서 중요한 부분이 NodePort이다.

예를 들어 Ingress Controller Service가 다음과 같다고 가정한다.

```
Service
type: NodePort

port: 80
targetPort: 80
nodePort: 30080
```

그러면 다음과 같이 모든 Node의 IP에서 NodePort에 접근할 수 있다.

```
Node1:30080
Node2:30080
Node3:30080
```

여기서 나는 처음에 ngress Controller Pod가 Node2에 있으니까 Node2의 30080만 Ingress Pod로 연결된다라고 생각했다.

그렇지 않다.

Node1에 Ingress Controller Pod가 없더라도 Node1의 NodePort를 통해 해당 Service의 Endpoint로 전달될 수 있다.

예를 들어:

```
             NodePort 30080
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
   Node1:30080 Node2:30080 Node3:30080
       │          │          │
       └──────────┼──────────┘
                  ▼
       Ingress Controller Pod
             Node2:80
```

따라서 NodePort의 핵심은

- 모든 노드에 동일한 외부 진입 포트를 제공하고, kube-proxy가 Service의 백엔드 Endpoint로 연결되도록 만드는 것

이라고 이해하는 것이 정확하다.

---

# 4. Service는 실제 패킷을 전달하는 프로세스가 아니다

여기서 Service의 역할을 다시 정리할 필요가 있다.

Service 자체가 프로세스로 실행되는 것은 아니다.

Service는 Kubernetes API 객체이며, Control Plane의 etcd에 상태가 저장된다.

```
kubectl apply
     │
     ▼
 API Server
     │
     ├──────────────► etcd
     │                  │
     │              Service 저장
     │                  │
     │◄─────────────────┘
     │
     │  Watch event
     │  "Service가 변경됨"
     │
     ▼
 kube-proxy
     │
     │ Service / EndpointSlice 정보 확인
     ▼
SyncProxyRules()
     │
     ▼
IPVS / iptables 규칙 갱신
```

그리고 kube-proxy는 api-server를 구독하고 있다가, service 반영 내용을 보고 kube-proxy 규칙을 구성한다.

하지만 이것만으로 패킷이 전달되는 것은 아니다.

Service에 연결된 실제 Pod 정보를 관리하기 위해 EndpointSlice가 사용된다.

```
Service
   │
   │ selector
   ▼
EndpointSlice
   │
   ├── Pod A
   ├── Pod B
   └── Pod C
```

EndpointSlice는 Service의 백엔드 Endpoint 정보를 관리하며, kube-proxy가 Service 트래픽을 라우팅하는 데 사용하는 정보의 원천이다.

따라서 조금 더 정확하게 표현하면:

```
Service
  │
  ├─ ClusterIP
  ├─ Port
  ├─ TargetPort
  └─ Selector
        │
        ▼
   EndpointSlice
        │
        ├─ Pod IP
        ├─ Pod Port
        └─ Node 정보
```

# 5. kube-proxy가 실제 노드의 데이터 플레인을 구성한다

이제 Node1에서 다음 요청이 들어왔다고 생각해보자.

```
192.168.2.80:59992
        ↓
192.168.2.61:30080
```

Node1의 커널이 패킷을 수신한다.

iptables 모드의 경우 kube-proxy가 구성한 NAT 규칙을 통해 NodePort Service와 Endpoint로 연결된다.

개념적으로는 다음과 같은 흐름이다.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/e81417c7-5f2c-43b6-8387-dd9d0eeefe8d" />


그림 1 iptables 기반 CNI 패킷 흐름

예를 들어

```
Node2:30080
     │
     ▼
KUBE-NODEPORTS
     │
     ▼
KUBE-SVC-XXXX
     │
     ▼
KUBE-SEP-XXXX
     │
     ▼
DNAT
192.168.2.62:30080
```

결국 패킷의 목적지가

```
192.168.2.61:30080
```

에서

```
192.168.2.62:30080
```

같이 node2의 Endpoint로 변경될 수 있다. 중요한점은 DNAT가 된 이후 라우팅이 수행된다는 점이다.

구체적인 체인 이름이나 구현은 kube-proxy의 모드와 Kubernetes 버전에 따라 달라질 수 있지만, 핵심은 kube-proxy가 Kubernetes API의 Service/Endpoint 정보를 바탕으로 노드의 패킷 처리 규칙을 구성한다는 것이다.

# 6. Ingress Controller는 

여기서 Ingress와 Ingress Controller를 분리해서 이해해야 한다.

```
Ingress
   =
"어떤 요청을 어디로 보낼 것인가?"
를 정의한 Kubernetes 객체

Ingress Controller
   =
Ingress 규칙을 실제 프록시 설정으로 구현하는 프로그램
```

현재 ingress rule은 다음과 같이 구성되어 있다.

```
spec:
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: main-svc
                port:
                  number: 80

          - path: /notices
            pathType: Prefix
            backend:
              service:
                name: notices-svc
                port:
                  number: 80

          - path: /notice-detail
            pathType: Prefix
            backend:
              service:
                name: notice-detail-svc
                port:
                  number: 80

          - path: /about
            pathType: Prefix
            backend:
              service:
                name: about-svc
                port:
                  number: 80
```

사용자가

```
GET /notices
```

를 요청하면 Ingress Controller가 HTTP 요청의 URI를 확인한다.

```
Ingress Controller
        │
        │ HTTP
        ▼
     /notices
        │
        ▼
  notices-svc
```

이것이 앞 단계의 NodePort와 가장 큰 차이다.

```
NodePort
    → TCP/IP 기반 Service 접근

Ingress
    → HTTP/HTTPS 요청의 Host, Path 등을 기반으로 라우팅
```

따라서 Ingress에서 문자열 기반 라우팅이라고 표현하기보다는,

> HTTP 요청의 Host와 URI Path 등의 HTTP 계층 정보를 기반으로 라우팅한다

라고 표현하는 것이 더 정확하다. Kubernetes Ingress 자체도 Host와 Path 등의 규칙을 사용해 트래픽을 백엔드로 매핑한다.

# 7. 중요한 오해: Ingress Controller가 매 요청마다 API Server를 조회하는 것은 아니다

처음 공부할 때 가장 헷갈렸던 부분이다.

```
Client
  ↓
Ingress Controller
  ↓
API Server 조회
  ↓
Service 확인
  ↓
Pod 확인
```

처럼 생각했었다.

하지만 실제 데이터 플레인에서 모든 HTTP 요청마다 API Server를 조회하는 구조로 이해하면 안 된다.

오히려 다음과 같이 이해하는 것이 좋다.

```
              Control Plane
                   │
              API Server
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
    Ingress                 Service
        │                     │
        ▼                     ▼
Ingress Controller       EndpointSlice
        │
        ▼
   Proxy Configuration
```

Ingress Controller는 Kubernetes API의 변경을 감시하고, Ingress/Service/EndpointSlice 등의 상태가 변경되면 자신의 프록시 설정을 갱신한다.

따라서 실제 요청이 들어왔을 때는:

```
Client
  ↓
Ingress Controller
  ↓
이미 구성된 Proxy Rule
  ↓
Backend
```

라는 데이터 플레인으로 동작한다고 이해하는 것이 좋다.

# 8. Ingress Controller에서 다시 Service Endpoint로 이동한다

예를 들어 /notices 요청이 들어왔다고 하자.

```
Client
   │
   ▼
HAProxy
   │
   ▼
NodePort
   │
   ▼
Ingress Controller
   │
   │ HTTP Path 확인
   ▼
/notices
   │
   ▼
notices-svc
   │
   ▼
EndpointSlice
   │
   ├── 10.233.71.42
   └── 10.233.xx.xx
```

여기서 Ingress Controller는 Service를 통해 백엔드 Pod로 연결한다.

중요한 점은 Ingress Controller가 반드시 Kubernetes Service의 ClusterIP로만 트래픽을 보내야 하는 것은 아니라는 점이다.

그리고 svc의 endpointslice 정보를 바탕으로 ingress는 아래처럼 upstream list를 구성한다.

svc의 endpointslice에서 pod에 대해 헬스체크가 실패하거나 정보가 변경되면, 아래 내용도 그에 맞게 바뀐다.

```
upstream prod-main-svc-80 {
    server 10.233.102.149:80;
    server 10.233.102.71:80;
    server 10.233.102.75.20:80;
}
```

Controller 구현에 따라 Endpoint 정보를 이용해 실제 Pod Endpoint로 직접 프록시할 수도 있다.

따라서 다음 두 개념을 구분해야 한다.

```
Ingress Rule
    ↓
어떤 Service를 사용할 것인가?

Service / EndpointSlice
    ↓
그 Service의 실제 Backend Endpoint는 무엇인가?
```

# 9. 다른 노드의 Pod라면 Calico가 개입한다

예를 들어 Ingress Controller가 Node2에 있고 Backend Pod가 Node1에 있다고 하자.

```
Node2
┌─────────────────────┐
│ Ingress Controller  │
│                     │
│        │            │
│        ▼            │
│  Backend Pod IP     │
│  10.233.71.42       │
└─────────┬───────────┘
          │
          │ Pod Network
          ▼
        Node1
┌─────────────────────┐
│ Backend Pod         │
│ 10.233.71.42        │
└─────────────────────┘
```

이때 중요한 것은 Kubernetes가 단순히

```
Pod IP → Node IP
```

를 자동으로 아는 것이 아니라, CNI가 Pod 네트워크를 실제 노드 네트워크 위에서 전달할 방법을 제공한다는 것이다.

현재 환경에서는 Calico가 이 역할을 담당한다.

---

# 10. Calico가 Pod-to-Pod 경로를 제공한다

Calico가 Pod 네트워크를 구성하는 방식은 크게 다음과 같이 볼 수 있다.

```
Pod A
 │
 ▼
veth
 │
 ▼
Node1
 │
 ├── Route Table
 │
 ├── Calico
 │
 └── VXLAN / 일반 IP routing
 │
 ▼
Node2
 │
 ▼
veth
 │
 ▼
Pod B
```

핵심은 Pod IP를 목적지로 하는 패킷이 최종적으로 올바른 Node까지 전달될 수 있어야 한다는 것이다.

예를 들어

```
10.233.75.25
```

가 Node2의 Pod라면 Node1에서는 해당 Pod CIDR 또는 Pod IP에 대한 경로를 알아야 한다.

```
10.233.75.0/26
       ↓
   Node2
```

이러한 경로는 Calico가 구성하는 라우팅 또는 캡슐화 메커니즘을 통해 제공된다.

---

# 11. VXLAN을 사용하지 않아도 Pod IP로 전달할 수 있는 이유

Pod IP가

```
10.233.75.25
```

이고 Node2가:

```
192.168.2.62
```

라고 하자.

Node1이 다음과 같은 경로를 알고 있다면

```
10.233.75.0/26 via 192.168.2.62 dev cali*
```

Pod IP를 직접 목적지로 하는 패킷을 일반 IP 라우팅으로 전달할 수 있다.

```
Pod A
  │
  ▼
Node1
  │
  │ route
  │
  ▼
192.168.2.62
  │
  ▼
Node2
  │
  ▼
Pod B
```

> VXLAN이 없으면 Pod 통신이 불가능한 것이 아니라, VXLAN 없이도 Pod CIDR에 대한 적절한 라우팅 정보가 있다면 전달할 수 있다.

Calico는 일반적으로 network overlay/encapsulation 없이 실행하는 것을 권장하며, 이 경우 workload IP를 네트워크가 인식하도록 static route 또는 BGP route distribution 같은 L3 routing 기술을 사용할 수 있다고 설명한다.
출처: https://docs.tigera.io/calico/latest/networking/configuring/vxlan-ipip

bgp를 활성화할 경우 일일히 각 노드에 라우팅 정보를 구성할 필요가 없다.

예를 들어 pod 네트워크가 다음과 같이 구성되어 있다고 해보자.

```
Node1 → Pod CIDR 10.233.71.0/24
Node2 → Pod CIDR 10.233.72.0/24
Node3 → Pod CIDR 10.233.73.0/24
```

bgp를 사용하면

```
              BGP
        ┌──────────────┐
        │              │
      Node1          Node2
        │              │
10.233.71/24     10.233.72/24
        │              │
        ▼              ▼
      Pods           Pods
```

각 노드가 자신이 가지고 있는 Pod CIDR를 다른 노드로 광고한다.

예를 들어 Node2가 아래 경로를 bgp를 통해 광고한다면

10.233.72.0/24
next-hop = 192.168.2.62

node1, node3는 라우팅 테이블에 아래 경로를 가지게 된다.

10.233.72.0/24 via 192.168.2.62 dev cali*

그러면 아래처럼 ip routing을 통해 목적지 pod까지 전달될수 있다.

```
Pod A
10.233.71.10
     │
     │ destination = 10.233.72.10
     ▼
Node1
     │
     │ route:
     │ 10.233.72.0/24
     │ via 192.168.2.62
     ▼
Node2
     │
     ▼
Pod B
10.233.72.10
```

# 12. CrossSubnet에서는 왜 VXLAN이

현재 실습 환경처럼 모든 Node가

```
Node1 192.168.2.61
Node2 192.168.2.62
Node3 192.168.2.63
```

처럼 같은 서브넷에 있다면 CrossSubnet 설정에서는 같은 subnet 내부의 트래픽에 대해 VXLAN 캡슐화를 하지 않는게 더 합리적이다.

```
같은 Subnet

Node1
  │
  │ 일반 IP routing
  ▼
Node2
```

반대로 Node가 서로 다른 subnet에 있다면

```
Subnet A
Node1
 │
 │ VXLAN
 ▼
Router
 │
 ▼
Subnet B
 │
 ▼
Node2
```

와 같이 VXLAN을 사용할 수 있다.

Calico의 CrossSubnet은 목적지 Node가 다른 subnet에 있을 때만 VXLAN을 사용하는 방식이며, 같은 subnet에서는 캡슐화를 생략할 수 있다.

따라서 현재 환경에서

```
Node1 ───────── Node2
192.168.2.61    192.168.2.62
```

가 같은 subnet이기에

```
Pod A
 ↓
Node1 ens33
 ↓
Node2 ens33
 ↓
Pod B
```

처럼 전달될 수 있다.

반면 서로 다른 subnet이라면:

```
Pod A
 ↓
Node1
 ↓
VXLAN encapsulation
 ↓
Node2
 ↓
Decapsulation
 ↓
Pod B
```

가 될 수 있다.

# 13. CrossSubnet의 전제 조건

여기서 중요한 전제가 하나 있다.

CrossSubnet으로 설정했다고 해서 Calico가 무조건 일반 라우팅을 사용할 수 있는 것은 아니다.

앞서 말했듯, 일반 라우팅을 사용하려면 Node가 원격 Pod 네트워크로 가는 경로를 알고 있어야 한다.

예를 들어 Node1에서:

```
ip route get 10.233.75.25
```

결과가 다음과 비슷하다면:

```
10.233.75.25 via 192.168.2.62 dev cali*
```

일반 라우팅으로 Node2까지 전달할 수 있다는 의미다.

반대로 해당 경로가 없으면

```
RTNETLINK answers: Network is unreachable
```

또는 잘못된 인터페이스가 선택될 수 있다.

```
같은 subnet
    ↓
일반 routing 가능
    ↓
VXLAN 생략

다른 subnet
    ↓
underlay가 Pod IP를 직접 라우팅하기 어려움
    ↓
VXLAN 사용
```

으로 이해하는 것이 좋다.

# 14. 전체 요청 흐름을 다시 연결하면

지금까지의 내용을 하나의 요청으로 연결하면 다음과 같다.

```
① Client
   │
   │ HTTP Request
   ▼
② HAProxy
   │
   │ TCP Load Balancing
   ▼
③ Node2:30080
   │
   │ NodePort
   ▼
④ kube-proxy
   │
   │ Service / Endpoint 규칙
   ▼
⑤ Ingress Controller Pod
   │
   │ HTTP
   │ /notices
   ▼
⑥ Ingress Rule
   │
   ▼
⑦ notices-svc
   │
   ▼
⑧ EndpointSlice
   │
   ▼
⑨ Backend Pod
```

Backend Pod가 다른 Node에 있다면:

```
⑧ EndpointSlice
        │
        ▼
   Backend Pod IP
   10.233.x.x
        │
        ▼
   Calico routing
        │
        ├── 일반 routing
        │
        └── VXLAN CrossSubnet
        │
        ▼
     Backend Node
        │
        ▼
     Backend Pod
```

결국 하나의 HTTP 요청이

```
L4
HAProxy
   ↓
NodePort

L3/L2
kube-proxy
   ↓
Calico
   ↓
Pod Network

L7
Ingress Controller
   ↓
Host / Path
   ↓
Service
   ↓
Backend
```

라는 여러 계층을 거쳐 이동한다고 볼 수 있다.

# 15. 이번 실습을 통해 이해한 핵심

이번 실습에서 가장 중요한 것은 Ingress 자체가 아니라 각 구성요소의 책임을 분리해서 이해하는 것이었다.

이렇게 역할을 나누어 보면 각각의 구성요소가 서로 중복되는 것이 아니라 서로 다른 계층에서 동작한다는 것을 알 수 있다.

# 16. 직접 확인할 수 있는 명령어

이론만 이해하는 것보다 실제 패킷과 규칙을 확인하는 것이 훨씬 효과적이었다.

### Service

```
kubectl get svc -A
kubectl describe svc <service>
```

### EndpointSlice

```
kubectl get endpointslice -A
kubectl describe endpointslice <name>
```

EndpointSlice가 실제로 어떤 Pod Endpoint를 가지고 있는지 확인할 수 있다.

### Ingress

```
kubectl get ingress -A
kubectl describe ingress <name>
```

### Ingress Controller

```
kubectl get pod -n ingress-nginx -o wide
```

### NodePort

```
kubectl get svc -n ingress-nginx
```

### kube-proxy 규칙

iptables 모드라면:

```
iptables-save -t nat | grep -E \
'KUBE-NODEPORTS|30080|KUBE-SVC|KUBE-SEP'
```

또는:

```
iptables -t nat -L KUBE-SERVICES -n -v --line-numbers
iptables -t nat -L KUBE-NODEPORTS -n -v --line-numbers
```

### Pod의 실제 네트워크 경로

```
ip route
ip route get <REMOTE_POD_IP>
```

### Calico

```
ip link show vxlan.calico
```

그리고 Calico IPPool에서:

```
kubectl get ippool -o yaml
```

또는 환경에 따라:

```
calicoctl get ippool -o yaml
```

vxlanMode: CrossSubnet인지 확인한다.

# 마무리

Ingress를 단순히 외부 요청을 Service로 연결해주는 것이라고 생각했다.

하지만 실제로는 하나의 요청이

```
HAProxy
  ↓
NodePort
  ↓
kube-proxy
  ↓
Ingress Controller
  ↓
Ingress Rule
  ↓
Service / EndpointSlice
  ↓
Calico
  ↓
Backend Pod
```

라는 여러 계층을 통과한다.

이 과정을 직접 확인하면서 Kubernetes 네트워크는 각각의 구성요소가 독립적으로 동작하는 것이 아니라,

Control Plane에서 정의한 상태를 각 노드의 Data Plane이 실제 패킷 처리 규칙으로 구현하고, CNI가 Pod 네트워크를 연결하는 구조

라는 것을 이해할 수 있었다.

특히 이번 실습에서 가장 중요했던 부분은 다음과 같다.

> Service는 패킷을 전달하는 프로세스가 아니라 원하는 Backend 집합을 표현하는 추상화이고, EndpointSlice는 실제 Endpoint 정보를 제공하며, kube-proxy가 이를 기반으로 Node의 Service 데이터플레인을 구성한다.

그리고 Ingress Controller는 그 위에서 HTTP/HTTPS 계층의 Host와 Path를 해석하여 적절한 Backend로 프록시한다.

따라서 다음과 같이 기억하면 전체 구조를 가장 쉽게 설명할 수 있다.

```
Service
  → "어떤 Backend 집합인가?"

EndpointSlice
  → "그 Backend의 실제 Endpoint는 무엇인가?"

kube-proxy
  → "Node에서 Service 트래픽을 어떻게 전달할 것인가?"

Calico
  → "Pod IP까지 실제 네트워크를 어떻게 연결할 것인가?"

Ingress Controller
  → "HTTP 요청을 어떤 Service로 보낼 것인가?"

HAProxy
  → "외부 TCP 연결을 어떤 Kubernetes Node로 보낼 것인가?"
```

이렇게 각자의 책임을 분리해서 이해하면 Kubernetes 네트워크에서 문제가 발생했을 때도 어느 계층에서 문제가 발생했는지 역추적하기 쉬워진다.
